# Device Type JSON Flash Compression — Proposal

## Status

**Not for now — parked (2026-10-13).** Investigated and prototyped but not scheduled. The expected saving
(15–18 KB, about 1% of the Axiom1 app image) doesn't justify the work yet. Revisit if flash becomes tight
or the device type sets grow substantially. The measurements reflect the device type sets as of this date.
The questions in §8 haven't been decided.

## 1. Summary

The device type records generated by `scripts/ProcessDevTypeJsonToC.py` store about 31 KB of JSON text in
flash. 89% of that is the `devInfoJson` and `pollInfo` strings.

The idea that started this was to replace common character sequences such as `","` with single bytes in the
range 0x80–0xFF. It works: these files contain no non-ASCII bytes, so that range is free. A hand-picked list of
punctuation sequences saves 26–30%.

The same mechanism gets about twice the saving if the substitutions are **learned at build time** instead of
hand-picked. Each byte 0x80–0xFF stands for a *pair* of bytes, and either half of the pair can itself be one of
these codes. This is a byte-pair (or "re-pair") encoding:

- **Saving:** the strings shrink to 35–44% of their size, including the 256-byte table. That's 15–18 KB less
  flash per build.
- **Decoder:** about 110 bytes of code and a 32-byte stack.
- **Speed:** a record decodes in well under a millisecond.

**Recommendation:** use learned pair encoding for `devInfoJson` and `pollInfo`, and **decode on access into
RAM** rather than teaching RaftJson to parse encoded text. Every runtime user of these strings already copies
them into a `String` or `RaftJson` before use. So decoding on access needs no extra RAM beyond the copy each
user already makes, and the parser stays untouched.

That's an honest 1% of the current Axiom1 app image (1.79 MB). It's worth doing because the decoder is tiny and
low-risk, and because the device type sets keep growing. It isn't a large win in absolute terms.

## 2. Current State

### 2.1 What's stored

Each `DeviceTypeRecord` (`components/core/DeviceTypes/DeviceTypeRecord.h`) holds `const char*` pointers to six
strings. The generator emits them as raw string literals in `DeviceTypeRecords_generated.h`, with
`json.dumps(..., separators=(',', ':'))` removing whitespace from the two JSON fields.

Measured from the source JSON, exactly as the generator emits it (bytes include terminators):

| Field | RaftCore set (49 types) | Axiom1 set (47 types) |
|---|---:|---:|
| `deviceType` | 456 | 516 |
| `addresses` | 312 | 217 |
| `detectionValues` | 852 | 1,014 |
| `initValues` | 1,649 | 1,651 |
| `pollInfo` | 1,801 | 2,125 |
| `devInfoJson` | 25,848 | 25,302 |
| **Total** | **30,918** | **30,825** |

Other things worth knowing about these strings:

- **Compiled size:** in the Axiom1 build, `DeviceTypeRecords.cpp.obj` has a 31,100-byte `.rodata.str1.1`
  section, which is these strings plus a few log messages. That's 1.7% of the 1,787,344-byte app image.
- **Record sizes:** `devInfoJson` is a median of about 380 bytes per record. The largest are LSM6DS (1.5 KB) and
  one Axiom type (3.3 KB).
- **No duplicates:** every `devInfoJson` is unique, so the linker's string merging doesn't help.
- **ASCII only:** neither set contains any byte at or above 0x80.
- **Key names:** these are 34–37% of `devInfoJson` (`"n":`, `"t":`, `"o":`, `"r":` and so on in every attribute
  of `resp/a`). That's why a learned table does so well.

### 2.2 How the strings are used at runtime

This drives the design. Every use either copies the string or only compares/logs it:

| Use | Location | What it does |
|---|---|---|
| Poll config | `DeviceTypeRecords.cpp:208` | `RaftJson pollInfo(pDevTypeRec->pollInfo)` copies to RAM |
| Init/detection values | `DeviceTypeRecords.cpp:432, 668` | copied into `String` |
| Device info to clients | `DeviceTypeRecord::getJson()` → `getDevTypeInfoJsonByTypeIdx/Name` (`DeviceManager.cpp:1015, 1054, 1057`) | copied into `String` |
| `_conf` actions | `DeviceManager.cpp:1433` | `RaftJson devInfoJsonDoc(devTypeRec.devInfoJson)` copies to RAM |
| Logging | RaftI2C `DeviceIdentMgr.cpp:132, 171` | printed with `%s` |
| Data logger | Axiom1 `DataLogger.cpp:763` | `RaftJson pollInfo(devTypeRec.pollInfo ...)` copies to RAM |
| Type name compares | `DeviceTypeRecords.cpp:177`, Axiom1 `VL53LxCXSysMod.cpp:178`, … | `deviceType` compared as a C string |

Nothing parses `devInfoJson` or `pollInfo` in place from flash. That's different from the SysType
configuration, which RaftJson does read in place (see §7).

## 3. Options Evaluated

All figures are the **remaining size as a percentage of the original**, including any table or dictionary that
has to be stored. The input is `devInfoJson` + `pollInfo`: 27,649 bytes for RaftCore and 27,427 bytes for
Axiom1. The method is described in §9.

| | Scheme | RaftCore | Axiom1 | Decoder | RAM while decoding |
|---|---|---:|---:|---|---|
| A | Fixed list of 19 punctuation sequences (`","`, `":"`, `"},{"`, …) → single bytes | 70.5% | 74.3% | Trivial | Output only |
| B | Learned substring dictionary, 128 entries, non-recursive | 51.2% | 58.5% | Trivial | Output only |
| **C** | **Learned pair table, 128 codes, recursive** | **35.0%** | **44.2%** | **~110 B code** | **Output + 32 B stack** |
| C′ | As C with only 64 codes | 45.3% | 54.0% | ~110 B | Output + 32 B |
| D | Deflate per string (ROM `tinfl`) | 49.1% | 55.0% | In ROM | Output + ~11 KB |
| E | Deflate per string + 1 KB preset dictionary | 41.8% | 46.7% | In ROM | Output + ~11 KB + dictionary |
| B+D | B, then deflate per string | 38.4% | 44.9% | B + ROM | Output + ~11 KB |
| F | Deflate the whole set as one blob | 17.2% | 25.0% | In ROM | **Whole set expanded (~27 KB)** + ~11 KB |

What the table shows:

- **A (the original idea)** is sound but leaves most of the gain unused. The real redundancy is longer: key names
  with their surrounding punctuation (`{"n":"`, `","t":">h","u":"`), repeated values (`"r":[0,65535]`,
  `"o":"float"`) and whole common fragments. A fixed list also has to be maintained by hand.
- **C** finds those sequences automatically and nests them, so a single byte can stand for something like
  `"},{"n":"`. It's the best per-string scheme here and beats per-string deflate. Deflate pays for its Huffman
  tables in every few-hundred-byte string, and its 32 KB window gets almost nothing from short inputs.
- **D/E** are free in code terms: `tinfl_decompress` is in the ROM of the ESP32, S2, S3 and the C-series, according
  to the ESP-IDF 6.1 ROM linker scripts. But the `tinfl_decompressor` state is about 11 KB, it does worse than C,
  and preset dictionaries add flash and complexity.
- **F** compresses best, but it isn't random access. Reading one record means inflating the whole set, so it only
  makes sense if the entire expanded set is kept in RAM, which would need PSRAM. That swaps 20 KB of flash for
  27 KB of RAM, which is the wrong trade for RaftJson's aims.
- **Applying C to all fields except `deviceType`** gives a similar ratio (38.2% / 46.5%), but the other fields
  are only about 3 KB, so that's a possible second phase rather than part of the first.

### 3.1 Approaches rejected

- **Teaching RaftJson to parse encoded text in place.** This was part of the original idea. Learned codes cross
  structural boundaries: one byte can close a string, close an object, open another and start a key. Every
  scanner function (key matching, brace and quote counting, string bounds, escapes, number tokens) would have to
  read through a token-expanding iterator. That would slow every RaftJson lookup, including on plain documents,
  and add risk to the parser code that was just hardened. Limiting codes so they never span `"`, `{`, `}`, `[`,
  `]`, `,` or `:` would keep in-place parsing possible, but it cuts the gain back to roughly scheme A. Since no
  caller parses these strings in place anyway (§2.2), decode on access is both simpler and better.
- **Leaving `devInfoJson` out of the firmware.** The generator already has an option for this (`--incdevjson`).
  But clients get device type info from the device, and `DeviceManager` reads `_conf` actions from it, so this
  isn't viable in general.
- **Shorter keys or positional arrays in `devInfoJson`.** This would remove much of the 34–37% spent on key
  names, but it changes a format that clients consume, such as the web apps and raftjs. Pair encoding gets most
  of that saving without changing anything clients see.

## 4. Proposed Design

### 4.1 Encoding

- **Bytes 0x00–0x7F** are ASCII as now, and 0x00 still terminates.
- **Bytes 0x80–0xFF** are codes. Code `c` expands to `table[c - 0x80][0]` followed by `table[c - 0x80][1]`, and
  each of those is either an ASCII byte or another code.
- **One table per build.** The table is learned from all the strings being encoded in that build, so it adapts to
  the device types each application actually includes. It's at most 128 × 2 = 256 bytes in flash.
- **Learning:** repeatedly replace the most frequent adjacent pair with a new code. Stop at 128 codes, or when the
  most frequent pair occurs fewer than 3 times, since a new code then saves nothing after its own two table bytes.
- **Nesting limit:** the generator also caps nesting depth (16), so the decoder's fixed stack can't overflow. The
  measured maximum depth is 11 for RaftCore and 7 for Axiom1.
- **Non-ASCII fallback:** if a string contains a byte at or above 0x80 (for example UTF-8 `°C` added in future),
  the generator stores that string unencoded and marks it as plain (§4.3), with a build warning. Nothing breaks;
  that string just isn't compressed.

### 4.2 Generator changes (`ProcessDevTypeJsonToC.py`)

1. **New option**, for example `--jsonencode pair` (default off initially, see §6). It's passed from
   `RaftBootstrapPhase2.cmake` / `RaftProject.cmake`, where the script is already invoked.
2. **Learn the table** over the `devInfoJson` and `pollInfo` strings of all records, after the existing compact
   `json.dumps`.
3. **Emit the table:** `static const uint8_t devTypeJsonPairTable[N][2] = {...};`.
4. **Emit encoded strings carefully.** Every byte at or above 0x80 needs a fixed-width escape: octal `\ooo`, or
   `\xHH` followed by closing and reopening the string literal. A C hex escape (`\x80a`) keeps consuming hex
   digits, so `\x80` followed by the letter `a` would silently become one wrong character.
5. **Emit the decoded length** of each encoded string (`uint16_t`), so the runtime can allocate exactly once.
6. **Self-check at build time.** The script decodes every encoded string with the same algorithm the firmware uses
   and stops the build if any doesn't match the original. A table or escaping bug then shows up at build time,
   not on a device.

### 4.3 Runtime changes (RaftCore)

- **`DeviceTypeRecord`** (it stays a POD):
  - The encoded fields get **new names**, for example `devInfoJsonEnc` and `pollInfoEnc`, alongside their decoded
    lengths and an encoding flag per field (plain or pair-encoded).
  - The rename is deliberate. Any code that still reads the old field names fails to compile, rather than quietly
    printing or parsing encoded bytes. It makes the compiler find every call site, including in RaftI2C and
    applications.
  - `DeviceTypeRecordDynamic` (records added at runtime) always uses plain text.
- **Accessors on `DeviceTypeRecord`:**
  - `String getDevInfoJson() const` decodes, or copies if the field is plain.
  - `RaftJson getPollInfoJson() const` decodes straight into a `RaftJson::JsonStrVec` and hands it over with
    `setSourceVec()`, which was added in the recent RaftJson work. That's one allocation, exactly the size of the
    copy callers make today.
  - `getJson()` uses these internally.
- **Decoder:** a static function (about 110 bytes of code) with an explicit 32-byte stack and a bounds-checked
  output, roughly:

  ```cpp
  // Expand pair-encoded text (codes 0x80..) - returns length or 0 on error (bad code, depth, or output full)
  size_t expandPairEncoded(const uint8_t* pIn, const uint8_t (*pTable)[2], uint32_t tableLen,
                           char* pOut, size_t outMax);
  ```

  It also checks codes against the table length, so a corrupt string can't index outside the table.
- **Call sites to update** (from §2.2):
  - RaftCore: `DeviceTypeRecords.cpp` (poll info), `DeviceManager.cpp:1429–1433`, and
    `DeviceTypeRecord::getJson()`.
  - RaftI2C: `DeviceIdentMgr.cpp` (two log lines).
  - Axiom1: `DataLogger.cpp:763`.
  - Other applications that read these fields directly will fail to compile until updated, because of the rename.

### 4.4 Cost at runtime

| | Today | With pair encoding |
|---|---|---|
| Flash (strings) | ~27.5 KB | ~9.7–12.1 KB + 256 B table |
| Code | — | +~110 B decoder, + small accessors |
| RAM while using a record | One copy of the string | One buffer of the same size (decoded into directly) + 32 B stack |
| CPU | `strlen` + copy | Decode at about 4.5 µs per KB on the host. On the ESP32-S3 it's estimated at well under 1 ms for the largest (3.3 KB) record; to be measured on the device. Records are decoded when a device is identified or its info is requested, not in polling loops. |

## 5. Wider Use

- **`detectionValues`, `initValues`, `addresses`:** these could use the same encoding later, about 3 KB more at a
  similar ratio. They're kept out of the first phase because they're small and parsed as plain strings in several
  places.
- **`deviceType`:** it's compared directly as a C string in several libraries, so it stays plain.
- **SysType configuration** (`SysTypeInfoRecs.h`, about 16 KB of source in Axiom1): RaftJson reads this in place
  from flash (`setSourceStr(..., false, ...)`) for the life of the application. Encoding it would mean keeping a
  decoded copy in RAM permanently. That's the opposite trade to the device types, so it's not proposed. It could
  be reconsidered for PSRAM-only builds if flash ever becomes tight.

## 6. Implementation Plan

1. **Generator:** the encoder, emitting the table, escapes and lengths, plus the build-time self-check. The option
   is off by default, so generated output doesn't change until enabled.
2. **Runtime:** the decoder, the `DeviceTypeRecord` rename, the accessors and the plain/encoded flag. Update the
   call sites in RaftCore, RaftI2C and Axiom1.
3. **Tests:**
   - Python: encode, decode and compare for both device type sets, a string with non-ASCII bytes (falls back to
     plain), and a forced nesting-depth limit.
   - RaftCore unit tests: the decoder (round trip, bad code, depth limit, output too small), and plain vs encoded
     records giving identical `getJson()`, `getDevInfoJson()` and `getPollInfoJson()` results.
   - On the device: Axiom1 with the option on. Compare the device info JSON published for each detected device
     with the output of a build with it off, and check the flash saving in the size report.
4. **Turn it on by default** once it has been checked on Axiom1 and one other application.

## 7. Risks

| Risk | Mitigation |
|---|---|
| An application reads the record fields directly | Renaming the fields makes this a compile error rather than corrupt output |
| Non-ASCII text added to device types | Per-field plain fallback, with a build warning |
| Encoding or escaping bug in the generator | Build-time decode-and-compare self-check |
| Corrupt or mismatched table | Decoder checks code range, depth and output size, and returns 0 |
| Readability of the generated header | Encoded strings are no longer human-readable in the header. Add a generator option to also write a plain `.json` side file for inspection. |

## 8. Questions to Decide

1. Should the encoding be on by default once checked, or stay opt-in per application?
2. Should `detectionValues` and `initValues` be included in the first phase (about 1.5–2 KB more saving)?
3. The field rename is a breaking change for code outside RaftCore that reads `DeviceTypeRecord` fields directly
   (RaftI2C, Axiom1). Is that acceptable, or should the old fields stay (always plain) for one release?

## 9. Appendix: How the Figures Were Measured

- **Input:** the strings were rebuilt from `RaftCore/devtypes/DeviceTypeRecords.json` and
  `RoboticalAxiom1/AxiomDevTypes/{DeviceTypeRecords,RSAOTypeRecords}.json`, using the same `json.dumps`
  separators as the generator.
- **Schemes:** A–F were run in Python. Deflate is `zlib` raw deflate at level 9. Preset dictionaries were built
  from the most frequent 8–64-character substrings.
- **Prototype:** a Python encoder emitted the pair table and the encoded strings for both sets. A C decoder with
  an explicit stack round-tripped every string correctly under AddressSanitizer and was timed on the host. Built
  with `xtensa-esp32s3-elf-gcc -Os`, the decoder is 109 bytes of `.text`.
- **Flash:** the compiled figure is the `.rodata.str1.1` section of `DeviceTypeRecords.cpp.obj` in the Axiom1
  ESP-IDF 6.1 build, measured with `xtensa-esp32s3-elf-size -A`.
